## Summary

Column 4 targets the HOSTED Redis Agent Memory service on Redis Cloud. Its data-plane API is {endpoint}/v1/stores/{storeId}/... with an `Authorization: Bearer <API_KEY>` header. The docs URL you gave (https://redis.io/docs/latest/develop/ai/context-engine/agent-memory/) is live and current, and the official machine-readable spec is published at .../agent-memory/api-reference/openapi-agent-memory.json. I fetched and parsed that spec. An official Python SDK exists: PyPI `redis-agent-memory` 0.4.1 (released 2026-09-16, Python >=3.10, Speakeasy-generated, depends on httpx and pydantic). It is unrelated to the open-source `agent-memory-server` / `agent-memory-client`, which use /v1/working-memory/... and return `dist`/`score` per result. The most important design fact is that the hosted search response has NO similarity score. `MemoryRecord` carries only id, text, memoryType, sessionId, ownerId, namespace, topics, attributes, createdAt and updatedAt. Any "with a similarity score" wow must therefore be derived by sweeping `similarityThreshold`; I tested that algorithm offline against a fake server and it recovers scores to ~0.001 in about 21 calls plus refinement. Direct long-term-memory creation (POST /long-term-memory, bulk) is the instant path. Automatic extraction from session events is asynchronous and runs on the store's extraction cadence (default 5 min, configurable 60-600 s), so allow minutes. It uses Redis-managed model credentials by default, so no customer LLM key is required for the notebook. Data lives in the Redis Cloud database chosen when the service was created (repo evidence in flush_redis.py and seed_memories.py, plus docs). The 3072-dim FLOAT32 HNSW COSINE index `memory:{storeId}:ltm` is what the demo repo recreates. Column 1 can show that index only if the user supplies the same database, and column 1 must never FLUSHDB or purge `memory:*` there. The store is shared with the live Iris demo, so every call must filter by a unique ownerId plus a fixed notebook namespace, and cleanup must delete by explicit IDs only.

## Verifier corrections (authoritative)

- **Claim:** 'The published spec and every quickstart still use the string `namespace`' (api_surface section 2)
  - **Correction:** Only the spec and the LangGraph tutorial use `namespace`. The REST API quickstart, the Python SDK quickstart, the Iris getting-started tutorial and its Colab never mention it (0 occurrences of 'namespace' in each). The recommendation to use the string label is still reasonable, but the justification overstates the docs.
  - **Source:** grep -c -i namespace on the fetched rest-api-quickstart, python-sdk-quickstart and getting-started-with-redis-iris pages and colab/agent_memory.ipynb = 0; LangGraph tutorial = 15
- **Claim:** HTTP 424 `type` is one of resource-unavailable, database-out-of-memory, and on model-backed calls invalid-model-credentials and model-quota-exceeded (presented in the api_surface Errors section alongside the published spec)
  - **Correction:** The published OpenAPI 1.0.0 lists only /errors/resource-unavailable and /errors/database-out-of-memory (FailedDependencyErrorType), and maps search's 424 to that same FailedDependencyErrorResponseContent. The two model-credential URIs exist only in SDK 0.4.1 (MemoryFailedDependencyErrorType). The docs name them only in prose ('Invalid Model Credentials', 'Model Quota Exceeded'). Treat the type as an open string and print it; do not switch on a closed enum.
  - **Source:** openapi-agent-memory.json components.schemas.FailedDependencyErrorType.enum and paths['/v1/stores/{storeId}/long-term-memory/search'].post.responses['424']; redis_agent_memory/models/memoryfaileddependencyerrortype.py (0.4.1)
- **Claim:** iris-demos' memory dashboard uses 'the same trick' as the Colab (text="", limit=25), and whether text:"" combined with a similarityThreshold behaves as filter-only listing is 'untested'
  - **Correction:** main.py:372-376 passes no similarity_threshold. memory_service.py:139-145 then falls back to connection.similarity_threshold, which is 0.7 (settings.py:14) or MEMORY_SIMILARITY_THRESHOLD. So iris-demos sends text="" WITH similarityThreshold, unlike the Colab, which sends none. The existing demo therefore already exercises the empty-text-plus-threshold case, but nothing in the repo shows whether it returns results. The notebook should omit similarityThreshold on its listing and cleanup calls, as the Colab does.
  - **Source:** redis-iris-demos/backend/app/main.py:372-376; backend/app/memory_service.py:139-145,157-165; backend/app/settings.py:14
- **Claim:** seed_memories.py SCANs+DELs and 'then re-runs FT.CREATE with a hard-coded DIM 3072' / 'recreates FT index'
  - **Correction:** FT.CREATE runs only when FT.INFO on memory:{store_id}:ltm raises, i.e. when the index is missing (seed_memories.py:92-96). The SCAN+DEL purge (lines 46-61) is unconditional and is the real hazard. Recreating the index happens only after a prior FLUSHDB. The safety advice (never copy it) still holds.
  - **Source:** redis-iris-demos/scripts/seed_memories.py:46-61, 79-120
- **Claim:** SDK debug logs (AGENT_MEMORY_DEBUG) would leak the API key
  - **Correction:** The SDK logs headers through httpx.Headers repr, which masks authorization as '[secure]' (tested: '%s' % httpx.Headers({'Authorization': 'Bearer SECRET'}) -> {'authorization': '[secure]'}). Debug logging does dump full request and response bodies, i.e. memory text. The real key-leak risk is printing a plain dict of headers, as in the raw-httpx helper: dict(headers) shows the key in clear text.
  - **Source:** redis_agent_memory/basesdk.py:259-265,281-286 (0.4.1); uv run --with httpx==0.28.1 repr test

# API surface: hosted Redis Agent Memory (Redis Cloud, Iris)

## 0. Two different products. Do not mix them up

| | HOSTED service (target of column 4) | Open-source `redis/agent-memory-server` (V0) |
|---|---|---|
| Paths | `/v1/stores/{storeId}/session-memory/...`, `/v1/stores/{storeId}/long-term-memory/...` | `/v1/working-memory/{session_id}`, `/v1/long-term-memory/search`, `/v1/memory/prompt` |
| Search result key | `items` | `memories` (+ `total`, `next_offset`) |
| Per-result score | NONE in the published spec | `dist` and optional `score` |
| Python package | `redis-agent-memory` 0.4.1 (`from redis_agent_memory import AgentMemory, models`) | `agent-memory-server` 0.15.2 / `agent-memory-client` 0.14.0 |
| Status | Managed Redis Cloud service, public preview. Self-managed on Kubernetes is a private preview | GitHub README calls V0 "an open research artifact, not the supported production distribution" |

The iris-demos `extract_memory_items()` accepts both `items` (hosted) and `memories` (OSS-legacy). For the notebook, read only `items`.

## 1. Connection

- Base URL = the console "Endpoint". It must include `https://`. The docs show no example value.
- Store ID = console "Store ID". The URL prefix is `{endpoint}/v1/stores/{storeId}`.
- Auth: `Authorization: Bearer <API_KEY>`. Also send `Accept: application/json`, and `Content-Type: application/json` on bodies. iris-demos prepends "Bearer " if the key lacks a Bearer/Basic prefix.
- Health: `GET {endpoint}/health` returns `{"status":"healthy"}`. `GET {endpoint}/v1/stores/{storeId}/health` returns `{"status":"healthy|degraded|unavailable","features":{"<name>":{"status":...}}}`. Feature names are unknown, so print the raw JSON. Use the store health call as the notebook's "test connection" button.
- iris-demos env names: `MEMORY_API_BASE_URL`, `MEMORY_STORE_ID`, `MEMORY_API_KEY` (optional `MEMORY_OWNER_ID`, `MEMORY_ACTOR_ID`, `MEMORY_NAMESPACE`, `MEMORY_SIMILARITY_THRESHOLD`, `MEMORY_LIMIT`). SDK env names: `AGENT_MEMORY_API_KEY`, `AGENT_MEMORY_STORE_ID`, `AGENT_MEMORY_DEBUG`. Official docs and Colab use `AGENT_MEMORY_URL` / `AGENT_MEMORY_ENDPOINT` / `AGENT_MEMORY_SERVER_URL`. The notebook should read `MEMORY_*` first, since that is what the owner already has, and fall back to `mo.ui.text` inputs.

## 3. Payloads (camelCase on the wire)

### Add session event
```
POST /session-memory/events
{"sessionId":"ib-ab12cd34-s1",      // optional; server generates a 32-char hex id if omitted
 "actorId":"ib-ab12cd34",           // REQUIRED, ^[a-zA-Z0-9-]+$, max 64 in the spec
 "role":"USER",                     // USER | ASSISTANT | SYSTEM (uppercase)
 "content":[{"text":"..."}],        // only content-part type is {"text"}
 "createdAt":"2026-09-29T12:00:00Z",// REQUIRED RFC3339
 "namespace":"iris-basics-notebook",// optional; taken ONLY from the session's first event; extracted LTM inherits it
 "metadata":{"source":"iris-basics"}}   // any JSON
-> 201 {"event":{"eventId":"<32 alnum>","actorId","sessionId","role","content","createdAt","systemTimestamp","metadata"}}
```

### Get session
```
GET /session-memory/{sessionId}
-> {"sessionId","ownerId","namespace"?,"events":[SessionEvent...],
    "summary"?:{"text","summarizedUpToEventId","createdAt","updatedAt","metadata","summarizedEvents"}}
```
`ownerId` is "set from the actorId of the first event". With summarization on, `events` excludes already-summarised events and `summary` holds the compacted text. iris-demos ignores `summary`, which is a teachable gap.

### Bulk create long-term memory
```
POST /long-term-memory
{"memories":[{"id":"ib-ab12cd34-m1",   // REQUIRED client id, ^[a-zA-Z0-9-]+$, <=64 ("idempotent creation")
  "text":"...",                        // REQUIRED, 1-50000 chars
  "ownerId":"ib-ab12cd34",             // REQUIRED, ^[a-zA-Z0-9-]+$, <=64
  "memoryType":"semantic",             // optional: semantic|episodic|message|session_summary_view|<custom>; ^[a-zA-Z][a-zA-Z0-9_-]*$
  "sessionId":"ib-ab12cd34-s1",        // optional
  "namespace":"iris-basics-notebook",  // optional label (deprecated in SDK 0.4.1)
  "topics":["food","allergy"],         // optional, <=50 topics, each 1-100 chars
  "attributes":{}}]}                   // only for custom memory types
-> 201 {"created":["ib-ab12cd34-m1"],"errors":[{"id":"...","error":"..."}]}
```

### Search
```
POST /long-term-memory/search
{"text":"What should the kitchen avoid serving me?",  // "" = filter-only listing (used by the official Colab and by iris-demos main.py:372-376)
 "similarityThreshold":0.5,   // float 0-1, "minimum ... (normalized cosine similarity)"; server default when omitted is undocumented
 "limit":5,                   // 1-100, default 10
 "filterOp":"all",            // "all" | "any" (conjunction across the filter fields)
 "pageToken":"...",           // from nextPageToken
 "filter":{
   "ownerId":   {"eq":"..."},                   // clause operators: eq, ne, in[], all[]   (NOT "any"); case-SENSITIVE
   "sessionId": {"eq":"..."},                   // same operators; case-sensitive
   "namespace": {"eq":"..."},                   // same operators; case-INSENSITIVE. eq/in/all never match records with no namespace; `ne` DOES
   "topics":    {"in":["a","b"]},               // eq|ne|in|all; case-insensitive
   "memoryType":{"in":["semantic","episodic"]}, // eq|ne|in|all; case-insensitive
   "createdAt": {"gte":"2026-09-29T00:00:00Z"}, // gt|gte|lt|lte|eq (RFC3339)
   "attributes":{"<field>":{"string":"x"}}      // one of {"string"}|{"number"}|{"boolean"}|{"list":[...]} (custom types only)
 }}
-> 200 {"items":[{"id","text","memoryType"?,"sessionId"?,"ownerId"?,"namespace"?,"topics"?,"attributes"?,"createdAt","updatedAt"}],"nextPageToken"?}
```
There is NO search-mode field. The docs say "semantic, keyword, or hybrid" retrieval, but neither the spec nor SDK 0.4.1 exposes a selector. The response has NO score or distance.

### Bulk delete / delete session
```
DELETE /long-term-memory   body {"memoryIds":["id1","id2"]}  -> 200 {"deleted":[...],"errors":[...]?}
DELETE /session-memory/{sessionId}                           -> 204 (no body; 404 if absent - treat as already clean)
```

### Errors
The body is RFC 7807-like: `{"title","status","detail","instance","type"}`. Statuses: 400, 401, 403, 404, 408, 413, 424, 429, 500 (SDK also has 423 resource-suspended and 409 for namespace ops).

HTTP 424 = Failed Dependency: "a dependent resource required to process the request is unavailable or unhealthy". Its `type` is one of:
- `/errors/resource-unavailable`
- `/errors/database-out-of-memory`
- (on model-backed calls, e.g. search / create / update) `/errors/invalid-model-credentials`
- (on model-backed calls) `/errors/model-quota-exceeded`

iris-demos passes `allow_424=True` on search, so a 424 silently becomes "0 memories". The notebook must instead print `type` and `detail`.

- Create payload (memory_service.py:217-229): `{"memories":[{"id","text","memoryType","ownerId","sessionId","namespace","topics"}]}`.

## Explorable parameters

- **similarityThreshold** — Minimum normalized cosine similarity for a long-term-memory hit. This is the main knob. The search response returns no score, so the slider effect shows as items appearing or disappearing, and a sweep can recover per-item bands. Values: float 0.0-1.0, slider step 0.05; use `is not None`, since 0.0 is valid _(src: openapi SearchLongTermMemoryRequestContent; iris-demos defaults 0.7 (settings.py:14), 0.5 (radish domain.py:296), 0.4 (workshop cell 20))_
- **limit** — Max results per search page. Combine with pageToken/nextPageToken for paging. Values: int 1-100 (default 10); mo.ui.slider or number _(src: openapi SearchLongTermMemoryRequestContent (default 10, range 1-100); iris-demos MEMORY_LIMIT default 6)_
- **text (query)** — Natural-language query embedded server-side. An empty string means filter-only listing, which is documented in the Iris Colab. Values: free text; "" to enumerate by filter _(src: openapi; https://redis.io/tutorials/getting-started-with-redis-iris/; main.py:372)_
- **memoryType** — Kind of long-term memory to write or filter by: semantic (durable facts), episodic (snapshot of one experience), message; also session_summary_view and up to 3 custom types defined in the console. Filter matching is case-insensitive. Values: semantic | episodic | message | (session_summary_view) | custom; filter ops eq/ne/in/all _(src: create-service (built-ins); overview (semantic vs episodic); openapi MemoryTypeFilter)_
- **topics** — Tag list on a memory (<=50 tags, each 1-100 chars). Filterable: `in` = any-of, `all` = must-have-all, eq/ne. Case-insensitive. Values: list[str]; mo.ui.multiselect of the run's known topics _(src: openapi CreateMemoryRecord.topics, TopicsFilter)_
- **filter.ownerId / filter.namespace / filter.sessionId** — Scope lens: owner isolation (case-sensitive), namespace grouping (case-insensitive; eq never matches records without namespace, ne does), and session scoping. Dropping sessionId turns a single-session lookup into multi-session recall, which is the core Agent Memory lesson. Values: eq | ne | in[] | all[]; toggle switches (search this session only / all my sessions / another owner) _(src: openapi LongTermMemoryFilter/NamespaceFilter; main.py memory_service._build_search_filter)_
- **filterOp** — How multiple filter fields combine: all = AND (default used by iris-demos), any = OR. Try topics-in-[...] plus memoryType-eq-episodic under both. Values: "all" | "any" (mo.ui.dropdown) _(src: openapi FilterConjunction)_
- **filter.createdAt** — Time-window filter for 'what did I learn since X'. Values: gt | gte | lt | lte | eq with RFC3339 timestamps _(src: openapi CreatedAtFilter)_
- **session vs long-term (tier)** — Session memory holds ordered events for one sessionId (TTL default 1 h, optional summary); long-term memory holds durable records searchable across sessions (TTL default 365 d). Contrast by reading GET session versus POST search from a brand-new sessionId. Values: n/a (architecture toggle in the UI) _(src: developer-guide; create-service Memory configuration)_
- **role / actorId / metadata (session event)** — Who spoke (USER/ASSISTANT/SYSTEM), an actor id (first event's actorId becomes the session ownerId), and free-form JSON metadata carried on the event. Values: role enum; actorId ^[a-zA-Z0-9-]+$ <=64; metadata any JSON _(src: openapi AddSessionEventRequestContent)_
- **includeSummarisedEvents / summary** — Show the compacted summary versus retained events after summarization has run (needs console summarization enabled and a low 'Summarize after' threshold). Values: bool query param; summary.text, summarizedEvents, summarizedUpToEventId _(src: openapi GetSessionMemoryResponseContent/SessionSummary; REST quickstart step 3)_
- **Console-only store settings (not settable via API)** — Short-term TTL (default 1 h), Long-term TTL (default 365 d), Extraction cadence (blank = 5 min; 60-600 s), Automatic summarization (Summarize after / Keep most recent), custom memory types, exclusions. Explain them in a markdown cell with a console link, since the notebook cannot read or change them. Values: cadence 60-600 s; TTL in seconds/minutes/hours/days _(src: create-service; view-service)_

## Safety concerns

- SHARED STORE: the store is the same one the live Iris demo uses, whose ownerIds look like CUST-DEMO-001 / CUST001 / P001 / ANALYST-DEMO-001 with namespaces like '<domain>-demo' and 'radish-bank-workshop'. Generate a per-run ownerId (for example 'ib-' + uuid4().hex[:8], alphanumeric plus hyphen, <=64) and use a FIXED notebook namespace (for example 'iris-basics-notebook'). Put BOTH filters, ownerId eq and namespace eq, in EVERY search, including the text='' listing. Never search with an empty filter, which would dump other tenants' memories.
- Never use list-sessions with includeAll=true (it exposes every session in the store). If sessions must be listed, use filterOwnerId=<this run's ownerId>. Session ownerId equals the first event's actorId, so start every session with a USER event with actorId=ownerId, and do not seed a session with an ASSISTANT greeting first.
- CLEANUP by explicit IDs only. Keep a list of every memory id the notebook creates (client ids like '<ownerId>-m1') and every sessionId. Delete via DELETE /long-term-memory {memoryIds} (<=100 per call) and DELETE /session-memory/{id} (204, treat 404 as already clean). For auto-extracted memories, whose ids are server-generated, enumerate with search text='' + filter {ownerId eq run, namespace eq notebook} and page with nextPageToken (limit<=100), then bulk-delete exactly those ids. Provide a 'Clean up' run_button, register a best-effort atexit hook, and re-verify by searching again to show 0 items.
- Namespace-wide 'sweeper' for leftovers from crashed runs: search filter {namespace eq 'iris-basics-notebook'} only, then delete those ids. This is safe only because that namespace is used exclusively by this notebook. There is no prefix filter (eq/ne/in/all only), so a random ownerId cannot be swept by prefix. Sessions self-expire via the short-term TTL (default 1 hour), so orphaned sessions are low risk, but extracted LTM outlives them and carries the session's namespace, which is why the namespace must be set on the first event.
- NEVER copy seed_memories.py's approach: it SCANs `memory:{store_id}:ltm:*` and DELs every key (all owners, all namespaces, including the live demo's) and then re-runs FT.CREATE with a hard-coded DIM 3072. Dropping or recreating the index, or deleting keys directly in Redis, corrupts the hosted service ('the Memory API won't rebuild [the index] automatically'). Every notebook Redis action against the memory DB must be read-only (FT.INFO, HMGET, HSTRLEN, SCAN with MATCH, FT.SEARCH).
- CROSS-COLUMN HAZARD: if column 1 (Redis Search) uses the same database as the Agent Memory store, its cells must never FLUSHDB/FLUSHALL, must never SCAN+DEL broad patterns, and must use its own key prefix, never `memory:`. flush_redis.py in iris-demos exists solely to preserve `memory:*` keys for this reason. State this in column 1's config cell if a shared REDIS_URL is used.
- Every session event can trigger LLM-based extraction and summarization billed to the store owner (Redis-managed or the owner's BYO provider key). Keep the notebook's traffic tiny (a handful of events, <~20 memories), and prefer direct LTM creation for the main demo. Do not loop-send events. Custom memory types configured on the shared store will also fire on notebook sessions and produce extra records, which the namespace/owner cleanup must include.
- Extraction is asynchronous and can fail silently (bad BYO key, quota). An empty result after the wait does not prove a bug. Show the elapsed time and the console cadence hint, and offer to skip. Surface 424 `type` and `detail` for synchronous calls rather than swallowing them the way iris-demos' allow_424 does.
- Capacity: each vector is 3072 x 4 = 12,288 bytes plus HNSW/metadata, and a Free 30MB database fills up (424 /errors/database-out-of-memory hits every co-tenant, including the live demo). Do not bulk-load, and clean up.
- Data governance: session content reaches the extraction model provider, and sensitive-data exclusions do not apply to directly created memories. Use only synthetic facts (fictional names, no emails/cards/SSNs) in the notebook.
- Secrets: collect the API key with mo.ui.text(kind='password'), read env vars first, never echo the headers dict, request objects or SDK debug logs (AGENT_MEMORY_DEBUG), and do not persist the key into the notebook file. marimo shows cell outputs, so a stray print(headers) leaks the key during a customer demo.
- Threshold-sweep wow (21+ calls) could hit undocumented 429 rate limits: add small sleeps, cap sweeps to on-click only (mo.ui.run_button), and handle 429 with a friendly message.
- The workshop_helpers `similarity_threshold or default` falsy-zero bug (line 399) means a slider at 0.0 silently queries at 0.7. Use `is not None` so the parameter-exploration cells tell the truth.

## Unknowns

- Whether the LIVE service ever returns an extra score/distance field on search items. The published spec and SDK 0.4.1 say no (verified), but responses could carry undocumented fields. Cannot be checked without a live call; the notebook should print one raw item once.

Only weak evidence: 0.4 excluded an unrelated memory in the workshop notebook; iris-demos defaults 0.7 and radish-bank uses 0.5.
