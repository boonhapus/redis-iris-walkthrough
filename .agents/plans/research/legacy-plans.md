## Summary

The three plans (v2, final, v3-onecomponent) describe a different product from the new spec: a single-component, single-credential marimo notebook titled "Redis Agent Memory - Interactive Internals Notebook". It rebuilds agent memory out of raw redis-py (LIST + HASH-with-vector + one FT.CREATE) and takes it apart in three linear Acts (run it, break it down in 4 panels, walk the code). It uses no hosted service, one secret (REDIS_URL), a local model2vec embedder, a client-side safety guard, and a vertical layout that explicitly says "avoid width=columns". The words LangCache and Context Retriever appear zero times in any plan or in the critic file (grep -c = 0), and the hosted Memory API appears only as a code-only "rung 3" that is never called. So the answer to "is this a 4-column notebook on the real hosted services?" is a firm no. `final` and `v3-onecomponent` differ by exactly one token (line 327: "**UNVERIFIED PEP 723 handling**" in v3 vs "**verified PEP 723 handling**" in final) plus a trailing newline; v3 is the newer file (Sep 14 21:21 vs 21:14) and its capitalised word is the safer one to trust, because molab's PEP 723 handling is still unverified (Day 0 item 1). The critic file critiques v2 (its section refs match v2's six-cell Act 1), and v3 already applied all 13 of its points. Most of the reusable value is engineering, not product: marimo mechanics (underscore names, run_button one-shot gating, lazy containers, show_code's greedy regex, run-vs-edit code visibility, setup-cell fragility), the guard/trace/consent/TTL/teardown safety model, uvx --sandbox delivery quirks, and Day-0/risk lists. I re-verified the marimo and redis-py claims on 0.24.2/0.25.0 and 7.4.0/8.1.0 in throwaway envs: every one held, but marimo's line numbers already drifted (session_manager.py:449 became :630). The older basics notebook implements roughly half the v3 plumbing (pinned uvx --sandbox, setup block, single guard+tracer class, consent cell, run_button gates, TTL, teardown, derived DIM) but none of the v3 content acts, and it was never run against a live Redis. It is also a third, different design (Agent Memory + LangCache + Semantic Routing, DIY equivalents, one credential).

## Explorable parameters

- **KNN k** — Number of nearest neighbours returned by FT.SEARCH '*=>[KNN k @vector $vec AS dist]'; KNN always returns k rows, so it cannot express a miss Values: default 3; DIALECT 2 required _(src: notebook.py:481; v3:188 (KNN 3))_
- **VECTOR_RANGE radius** — Cosine-distance cutoff for '@vector:[VECTOR_RANGE $r $vec]=>{$YIELD_DISTANCE_AS: dist}'; zero rows outside the radius = a cache MISS Values: slider 0.05-1.0 step 0.05, default 0.35; measured paraphrase 0.221 vs unrelated 0.825 with potion-base-8M _(src: notebook.py:518-520,556-562; readme.md:103)_
- **Index algorithm (FLAT vs HNSW)** — Vector index structure declared in the same one-line FT.CREATE schema; FLAT is exact at ~12 vectors, HNSW is the production choice Values: FLAT | HNSW; production memory index uses HNSW DIM 3072 COSINE (seed_memories.py:113-116) _(src: v3:189; notebook.py:339-353)_
- **DIM / VEC_BYTES** — Vector dimension fixed at FT.CREATE; derived from the embedder, never typed; different embedders cannot share an index Values: potion-base-8M = 256 dims / 1024 bytes; Iris routing 1536; hosted memory index 3072 _(src: v3:92; notebook.py:290-296; readme.md:108-111)_
- **DISTANCE_METRIC** — Schema-level metric (lives in the index, not the value) Values: COSINE (used everywhere); cosine distance on unit vectors = 1 - dot(a,b) (readme.md:95-96) _(src: v3:180; notebook.py:362)_
- **owner_id tag filter on/off** — Pre-filter that narrows candidates before the vector scan; removing it leaks other users' memories Values: (@owner_id:{alice}) | omitted | owner with no memories _(src: v3:188)_
- **Recency window size (LTRIM n)** — Size of the working-memory LIST; LLEN stays pinned while the index still recalls dropped turns Values: 5 (LPUSH ten times, LLEN stays 5) _(src: v3:91,179)_
- **TTL (session vs long-term)** — Session keys carry a TTL that counts down; LTM keys return -1; demo keys all expire Values: session TTL e.g. 861 s displayed; ltm -1; demo TTL constant 3600 s _(src: v3:91,301; notebook.py:43)_
- **Router REDUCE aggregator** — MIN vs AVG in FT.AGGREGATE GROUPBY; AVG makes a route with uniformly mediocre examples beat one strong example Values: MIN | AVG _(src: notebook.py:598,632,659-661)_
- **Per-route thresholds** — Applied AFTER the grouped result in a FILTER, with the query radius set to max(thresholds) Values: {'banking': 0.7, 'off_topic': 0.5} _(src: notebook.py:604-608,623-627)_
- **similarityThreshold / limit / filterOp / filter (hosted Agent Memory search)** — JSON request body fields of POST /v1/stores/{store_id}/long-term-memory/search (camelCase) Values: filterOp 'all'; filter keys ownerId, namespace, sessionId each {'eq': value}; limit int; similarityThreshold float _(src: redis-iris-demos/backend/app/memory_service.py:157-183)_
- **Memory shape thresholds read live** — CONFIG GET (never CONFIG SET) of hash-max-listpack-value, list-max-listpack-size (-2 = ~8 KB/node), etc. to show why encodings flip Values: read-only; Search-column internals content, optional _(src: v3:186,216-224)_

## Safety concerns

- Any Redis-touching column writes into the customer's (or SE's) real database, and new Essentials subscriptions reportedly allow ONE database, so a 'clean' DB usually does not exist (v3:328,464,481-485; plan assertion, not verified). Keep the plan's layers: per-session displayed prefix (demo:<run_id>:), key-position guard, consent cell showing DBSIZE and a zero-result scoped SCAN, TTL on every key, scoped teardown (SCAN MATCH prefix + UNLINK + FT.DROPINDEX incl. orphaned idx:demo:*), never FLUSHDB/FLUSHALL/CONFIG SET/MONITOR/KEYS (v3:141-150,298-303,449-451).
- Demo-repo hazard: redis-iris-demos scripts/flush_redis.py (called by make setup / reset / flush-redis) deletes EVERY key except memory:* (flush_redis.py:1-8,38-41). Never run those targets against a DB the new notebook (or a customer) also uses; and never use a memory: prefix, which belongs to the Memory API index memory:{store_id}:ltm (seed_memories.py:79-116).
- The Agent Memory service stores its data in the same Redis DB as the demo keys, so a Redis Search column doing FT._LIST/SCAN/teardown must stay strictly inside its own prefix and idx:demo:* names; the guard in the basics notebook does not scope FT.* index names (FT.DROPINDEX of any index passes) and only checks the first key of multi-key DEL/UNLINK (notebook.py:99-106).
- Four secrets will now sit in one notebook: use mo.ui.text(kind='password') for each, default from environment, never screenshot config cells (v3:307-308), no secrets in printed request logs (mask Authorization headers; the demo repo builds 'Authorization: Bearer <key>'), and treat pasting credentials into molab as a security-review question (v3:310).
- '--trusted' on a remote URL is a code-execution trust bypass; only ever against our own pinned tag URL, and document it in SAFETY.md (v3:308-309,326).
- The guard and tracer only see redis-py execute_command; pipelines, PubSub and all HTTP calls bypass both (v3:165, notebook.py:400-401). Hosted-service writes therefore need a separate scope check (fixed base URL/store/cache id/owner id per run) and an explicit cleanup path that the plan never designed.
- Transparency: on Essentials the credential is usually the 'default' user, i.e. can erase the database; say so on screen ('this credential can erase your database; the only thing stopping that is our client-side guard', v3:303). ACL SETUSER is reportedly unsupported on Redis Cloud (v3:292-294) so scoped users cannot be created for the demo.
- Scope creep into load: free Essentials is 100 ops/sec and 30 connections (plan assertion); avoid timers with default_interval, build each client once with explicit max_connections, keep lazy containers lazy so opening a section does not fire hosted-API calls (v3:93,248,285). Hosted services may bill or rate-limit per request.
- Consent-before-write ordering: read-only probes first (FT._LIST, DBSIZE, scoped SCAN), then a run_button naming host and key count, then any write including probe keys (v3:80-86; critic 3). Apply the same ordering to hosted stores before creating sessions/cache entries.
- Do not run destructive housekeeping against a shared demo/customer account: the plan's rule is 'no CONFIG SET, ever, checked at each dry run' (v3:311) and 'Never one shared database with thirty clients' (v3:329).
